# Pyokka handoff

Quokka.js for Python (3.12+) as a VS Code extension. Wire contract: `docs/PROTOCOL.md`.
History: `git log`, `CHANGELOG.md`. `package.json` is generated by `scripts/gen-manifest.py`.

## Decisions (do not relitigate)

- No tool-specific interpreter detection: Python extension env, `pyokka.python.interpreter`, or the picker.
- Only Automatic mode executes implicitly; On Save / On Demand queue everything until an explicit run.
  Default `onSave` for every file (2026-09-11; `smart` and `auto` stay selectable). The panel never
  writes the run mode to the user settings.
- Without re-running: hovers evaluate against the finished run, edited statements show `≈` shadow
  values, stale values on edited lines are hidden. Without a run only pure calls are evaluated (`python/pyokka_runtime/pure.py`: builtins like `len` and `sorted`, non-mutating methods of builtin types); a user function never runs from a hover, a watch or `eval`.
- `def`/`class` statements and class bodies are never steps.
- Library stepping is opt-in (`timeMachine.libraryCode`, `libraryPackages`), stdlib never.
- A library module's import-time execution is coverage-only (no steps, scopes, handled
  exceptions); library functions are stepped where stepped code calls them.
- Secrets are masked by provenance in the child (`pyokka_runtime/secrets.py`): secret-named env
  values anywhere, strings under secret names. Never by value shape (no prefix / entropy regex).
- Run children: a fork on Linux, a fresh interpreter on macOS and Windows
  (`pyokka_runtime/forksafety.py`, 2026-09-13). Forking on macOS died on every run after the
  first of a file that reaches an Apple framework (SIGABRT, `agent.py`, 2026-09-12): the parent
  has threads after run 1 and Apple's fork-safety check kills the child. Spawn costs about
  35 ms per run and needs no environment tricks; `PYOKKA_FORK=1` plus
  `OBJC_DISABLE_INITIALIZE_FORK_SAFETY=YES` brings the warm fork back for whoever wants it. A
  child killed by a signal is reported by name and never re-run. This Mac's Claude shell
  exports the objc variable, so the abort never shows from a Bash tool call: test with `env -u`.
- The debugger is the runtime's own pause at the frontier, not debugpy or DAP (2026-09-14,
  `docs/HANDOFF-debugger.md`): the hooks already know step, scope and depth, the child has a
  control channel, and agents drive it through the bridge. A DAP adapter may sit on top later.
- An explanation artifact generates its values, it never types them (2026-09-15,
  `docs/design/show-me.md`): `pyokka history` builds the code-history page's data by calling the
  same `RunSource` methods `context`, `var` and `why` call, and prints that command on every
  checkpoint as `verify`. `--prose` may fill only prose fields and fails on a generated one,
  which is what keeps the guarantee true once an agent starts editing. One skill,
  `skills/pyokka`, with modes `debug`, `explain` and `show` (2026-10-01; it replaced
  `pyokka-show-me`, `explain-code` and the `pyokka-agent` and `pyokka-debug` pointers).

- The side bar is this moment, the bottom panel is the whole run (2026-10-01). The Time Machine
  is a `pyokka` debug session in replay (`src/debug/replaySession.ts`, PROTOCOL "Replay debug
  session"): Call Stack, Variables, Watch and the debug toolbar show and move the current step.
  The panel draws no stack, no locals and no step buttons, in the Time Machine view or the
  Debugger view.

## Commands

```sh
scripts/check.sh                                   # typecheck + vitest + pytest + build
./node_modules/.bin/vscode-test                    # e2e; PYOKKA_UI_PASS=1 adds full-screen screenshots
scripts/release.sh                                 # bump + check + build + install + tag + GitHub release
node esbuild.mjs --production && ./node_modules/.bin/vsce package --no-dependencies   # build without releasing
code --install-extension "$PWD/pyokka-$(python3 scripts/version.py).vsix" --force   # then "Developer: Reload Window" everywhere
cd python && uv run --no-project python ../scripts/measure-library-run.py   # cold and warm cache
uvx --no-cache --from ./python pyokka run FILE --save run.json --library-code   # then story/step/context …
pyokka state --live --session FILE    # needs VS Code with pyokka.agentAccess on; see skills/pyokka
./node_modules/.bin/vscode-test --config .vscode-test.libdiag.mjs          # library run + Time Machine timings, example venv
command claude plugin validate --strict claude-plugin/pyokka-band   # the Claude Code band (also in check.sh)
command claude plugin test claude-plugin/pyokka-band                # its tests, against captured CLI JSON
python3 scripts/band-fixtures.py [--suspects "uv run --directory <bugs>/python python -m pyokka_runtime"]   # recapture that JSON
```

The band (`claude-plugin/pyokka-band`, marketplace `.claude-plugin/marketplace.json`) is a Claude
Code function-hooks plugin. The validator follows `$` only into functions declared in the same file
and reads `update`/`read` only of atoms declared there, so every function that takes `$`, and the
atoms, live in `hooks/register.tsx`; the other modules are pure (parse, narration, fix, plans, keys,
views). `.claude-plugin/types/` inside it is written by Claude Code when the mod loads and is ignored
by its own `.gitignore`; `tsc -p claude-plugin/pyokka-band` needs it, `validate` and `test` do not.

Test beds: `examples/demo.py`, `examples/rrf/` (the RRF demo and its FastAPI service) and the
fixtures under `test/unit/fixtures/` and `python/tests/`. A program that calls an LLM costs
tokens on every run: run it On Demand only, and never print the `.env` that holds its key.

## Versions and releases

Four files carry the version: `package.json` (the one that decides it), `python/pyproject.toml`,
`python/pyokka_runtime/__init__.py`, and the fallback literal in `scripts/gen-manifest.py`.
`scripts/version.py` is the only thing that writes them, and it writes all four together.

The level comes from a `Bump:` trailer on the commits since the last `vX.Y.Z` tag, patch when none
of them carries one. The subject line stays prose; the trailer sits in the body where
`git log --oneline` never shows it:

```
Debugger: the output stream verified against a program that is actually running

<body>

Bump: minor
```

`major`/`breaking`, `minor`/`feature`/`feat` and `patch`/`fix` are all understood. `.githooks/commit-msg`
rejects anything else, because a typo would fall back to patch and ship the wrong number. The hooks
live in `.githooks/`, which a fresh clone has to opt into once: `git config core.hooksPath .githooks`.

The next version is computed from the last tag rather than from the current number, so building five
times before committing lands on one new number instead of walking five. A commit that later says
`Bump: minor` still escalates that same pending release from 0.0.2 to 0.1.0.

Two things move it:

- `.claude/hooks/bump-version.sh`, a `PreToolUse(Bash)` hook, catches any command carrying
  `vsce package`, `--install-extension` or `esbuild.mjs --production` and bumps before it runs, so
  the vsix carries the new number rather than the previous release's. It skips `scripts/release.sh`,
  which bumps on its own, and `scripts/check.sh`, whose plain esbuild run is not a build anyone installs.
- `scripts/release.sh` does the whole pass: bump, `check.sh`, cut `## Unreleased` in `CHANGELOG.md`
  into a `## X.Y.Z` section, build, install, commit, annotated tag, push, and `gh release create` with
  the vsix attached. It refuses a dirty tree and refuses a release with no commits behind it.

Releases go to `ivorpad/pyokka`, each tag carrying its `pyokka-X.Y.Z.vsix`. The cut
changelog section is the release body, so the notes are the ones written while the work happened.

## Quirks

- Where `npm` is wrapped by `npq`, run `node_modules/.bin/*`. Where `cat`/`grep` are aliased, use
  `command cat`, `command grep`.
- Installing never restarts a running extension host; the status-bar tooltip shows the build stamp.
  Run reasons are logged per run in the Pyokka output channel (on disk under
  `~/Library/Application Support/Code/logs/*/window*/exthost/output_logging_*/`, UTC).
- The e2e launcher forces trust off; trust needs a dev host with a short fresh `--user-data-dir`.
- Spawn Agent without `name:`.
- Panel components render to HTML in vitest with `preact-render-to-string` (`test/unit/webview/chrome.test.tsx`);
  add a case there for anything the rail, toolbar or Settings view must show. The e2e suite
  cannot see inside the webview.
- Per-user state (session descriptors and sockets, `last-debug.json`, recent files, the library
  cache) lives under `$PYOKKA_HOME`, `~/.pyokka` when unset; `pyokkaHome()` in
  `src/util/paths.ts` and `pyokka_home()` in `python/pyokka_runtime/home.py` are the only
  resolvers. `.vscode-test.mjs` sets it to a fresh `/tmp/pk-e2e-*` per run and pytest to a
  per-test directory, so e2e and pytest never see the user's open windows (no more "2 live
  sessions match demo.py") and two e2e runs can go at once. A test that needs the directory
  reads `process.env.PYOKKA_HOME`; CLI children inherit it from the extension host.
- Instrumented library files are cached in `$PYOKKA_HOME/cache/`; `PYOKKA_CACHE_DIR` moves it,
  empty disables it (pytest does that per test). A stale-looking library run: clear it. An e2e
  run starts with an empty cache.
- `examples/demo.py` is pinned by line number and shape in the e2e suites (lines up to 91),
  in `python/tests/test_demo.py` (the `raise` line, the loop) and in
  `test_graph.py::test_demo_graph` (decisions, module statements, node count): an edit to
  the demo needs pytest as well as the e2e, even when no runtime file changed.
- Bash tool calls made in parallel share one cwd; a `cd python && ...` in one leaks into the
  others. Use absolute paths.
- Driving VS Code with cua-driver: the Cmd+K Q chord is unreliable (the `q` can land in the
  editor); use the command palette ("Pyokka: Start on Current File", "Developer: Reload
  Window"). Reload the window after every vsix install.
- The full e2e suite once failed the first four cases of `features.test.js` (no trace right after
  the Time Machine started) when `demo.test.js` ran before it; alone and on a rerun both were
  green (2026-09-14). Rerun once before blaming a change; the debugger specs
  (`debugger.test.js`, `debug-live.test.js`) run last and were not involved.
- The HTTP plugin (`pyokka_runtime.plugins.http_record`) loads on every run: HTTP Off observes
  the clients and lists the requests in the HTTP view; `pyokka.httpObserve: false` is the
  switch that leaves the clients untouched. A patch site that fails reports a `runner.error`
  and the run goes on.
- The extension runs the runtime from `dist/python` (esbuild copies `python/pyokka_runtime`
  there), also in a dev host (`code --extensionDevelopmentPath=<checkout> <project>`): after a
  Python edit run `node esbuild.mjs` again; the next run picks it up, no reload.
- Driving a dev host with cua-driver: AX presses on the panel's webview buttons are silent
  no-ops, pixel clicks off the screenshot work; the notification toast needed
  `delivery_mode: "foreground"`. A VS Code window that is covered by another one stops
  painting, so screenshots and parts of the AX tree go stale: check state through the bridge
  (`pyokka state --live --session FILE`, `walkthrough --live`) and the Pyokka output log.
- A `.claude/worktrees/<name>` checkout has no `node_modules`, `.vscode-test` or `python/.venv`:
  `uv run --group dev` in `python/` builds the venv; a symlink to the main checkout's
  `node_modules` and `.vscode-test` serves the JS checks (remove it before committing, the
  ignore rules match directories only). The e2e launcher fails under the long worktree path
  (`listen EINVAL … main.sock`: VS Code's IPC socket path is capped at 103 bytes): run it with
  a config whose `launchArgs` add `--user-data-dir=/tmp/<short>`.
- Where `npm` is `npq`, it gates an install on supply-chain findings and waits on stdin, so a
  non-interactive `npm install` looks like it succeeded and installed nothing (2026-09-15).
  `handlebars` trips it on maintainer dormancy and missing provenance attestations, neither of
  which is an advisory, and it intercepts `npx` too, so a test run goes through
  `./node_modules/.bin/vitest`; `command npm audit` is how you get a real audit, because `npm audit`
  goes to npq and reports on a package literally named `audit`.
- A headless-Chrome screenshot of a code-history page needs `--virtual-time-budget=3000` or it
  comes out blank, and the page turns off font ligatures on purpose (2026-09-15): without that,
  SF Mono draws the `--` of a `--json` in a `verify` line as one long dash, and the line exists
  to be copied.
- The code-history page is coloured by Shiki in the renderer, not in the browser (2026-09-15):
  `codeToTokens` runs against the file's lines and the tokens travel in the page's JSON, so the
  standalone page keeps its one property, nothing to fetch. Line-for-line alignment is checked
  before the tokens are kept. Dim now means opacity rather than a grey text colour, because the
  text colour belongs to the theme.
- A local's change marker is `(id(value), len(value))` (`tracer._record_locals`), so a re-bind
  inside a container is invisible: `scores[k] = scores.get(k, 0) + x` on a key that already
  exists keeps both, records no change, and `var` shows the value from before the statement
  (2026-09-15). Reproduce with the RRF demo: `pyokka var run.json scores` at #84, #96 and #102.
  The text now says `(same object)`, which is what was observed; it used to say `(unchanged)`,
  which asserted something about the program that was false, and two agents reading a run were
  misled by it. See the work item below for the fix.

three subagents, the last one started once the runtime's tests passed because its fixture

step) followed on 2026-09-12 on branch `worktree-values-as-of-step`: the pure rule and its
unit test committed first, then the decorator, the hover and the demo + e2e as three
subagents, the e2e one told to write first and run only once the other two had landed.
Item 9 (`pyokka why`, the provenance tree) was built 2026-09-12 on branch
`worktree-why-provenance` the same way, with a shared fixture program pinning the Python and
TypeScript builders to the same trees. "execute the handoff"
means: read this file, then the item's file, and start at its first step.
What was built on 2026-09-10 (agent access: `pyokka` CLI over saved runs, the VS Code
bridge behind `pyokka.agentAccess`, `--live`, `skills/pyokka-agent/`, since folded into `skills/pyokka`) is described there
too, with what is still open.

**Make a container's re-bind visible to `var` and `why`.** The marker above cannot see
`d[k] = v` on an existing key. Two fixes were measured on 2026-09-15 on a locals-heavy loop
(a 6-key dict accumulated over 20,000 iterations, median of 7 interleaved runs):

- Fold the item identities into the marker (`sum(map(id, val.values()))`, bounded): **+131%**
  wall time. The cost is the per-local call, not the element count, so a smaller bound does not
  help: bound 8 and bound 32 measured the same. Rejected.
- Have the instrumenter emit, per statement rid, the names that statement assigns, and deep-scan
  only those in `_record_locals`. O(1) per step and exact. This needs a new field on
  `file.instrumented` (or the original source kept on `InstrumentedFile` so `bindings.py` can
  build the table lazily), so it is a wire change and wants its own round.

Until then the label is honest and the limit is documented in the skill's CLI reference.
